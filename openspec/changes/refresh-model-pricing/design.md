## Context

应用是长期驻留的 Tauri 菜单栏程序。当前 `PricingTable` 在 `setup` 阶段加载后以不可变值存入 `AppState`，Popup 也只在首次挂载时调用一次 `get_pricing`。因此跨天运行不会重新读取当天缓存或远程价格，同一天的价格变化也没有用户触发入口。

现有远程请求使用 `reqwest::blocking`，超时 10 秒；现有价格文件按日期缓存，并已经具备“当天缓存 → 远程 → 历史缓存 → bundled fallback”的启动加载链路。本次改动应复用这些能力，不引入新的网络依赖或价格来源。

## Goals / Non-Goals

**Goals:**

- 应用不重启也能在跨天后自动应用新价格
- 电脑休眠、唤醒或后台检查延迟时，在下一次展示 Popup 后补充新鲜度检查
- 用户可以在设置窗口强制绕过当天缓存拉取远程价格
- 后台请求不阻塞 Tauri UI，刷新并发受到控制
- 刷新成功后已预热的 Popup 立即使用新价格，失败时继续使用旧价格

**Non-Goals:**

- 不提供逐模型价格编辑器或自定义远程地址
- 不修改 Agent 自带 `agent_cost` 的优先级
- 不改变 Token 日志、数据库 schema 或历史数据
- 不保证捕获远程源在同一天内的每次变化；同日变化由手动刷新获取

## Decisions

### 1. 使用可变共享状态保存当前价格表

将 `AppState.pricing` 改为 `RwLock<PricingTable>`。`get_pricing` 获取读锁并克隆，刷新成功后获取写锁替换整张价格表。价格读取频繁且更新极少，`RwLock` 比独占 `Mutex` 更符合访问模式。

另使用异步互斥锁串行化自动检查和手动刷新，避免多个 blocking 请求同时写入当天缓存。

### 2. 自动刷新采用“每小时检查 + Popup 展示时检查”

应用启动后创建独立后台任务，每小时检查当天是否已有有效缓存：存在则不访问网络；不存在则尝试远程拉取。Popup 展示时调用同一项新鲜度检查，覆盖系统休眠、定时器延迟和跨天后立即查看的场景。

不采用仅在本地午夜执行一次的定时器，因为休眠和系统时间变化可能错过执行；也不采用每小时强制远程请求，因为同一天缓存已经满足自动按日更新要求。

### 3. 手动刷新始终绕过当天缓存

新增 `reload_pricing` command，直接请求 LiteLLM，成功后写入当天缓存并替换内存价格表。网络、解析失败时返回错误，不使用 fallback 覆盖当前内存表。

自动路径使用 `ensure_pricing_fresh` command；它只在当天没有有效缓存时请求远程。两条路径共用相同的刷新与状态替换逻辑。

### 4. blocking 网络请求移出异步执行线程

保留现有 `reqwest::blocking` 实现，自动任务和异步 command 通过 `tauri::async_runtime::spawn_blocking` 执行网络和文件操作，避免阻塞 Tauri command/UI 调度。这样不需要同时维护同步、异步两套 HTTP 客户端。

### 5. 使用轻量事件通知前端重新读取价格

刷新成功后广播无大 payload 的 `pricing-updated` 事件。Popup 收到事件后重新调用 `get_pricing`，避免向所有 Webview 广播完整 LiteLLM 价格表。价格 state 更新会使现有费用派生计算立即重算，无需重扫 Token 数据。

### 6. 设置页提供明确的瞬时反馈

在“数据”标签增加模型价格行，说明价格每天自动更新，并提供“立即刷新”按钮。按钮在请求期间禁用并显示刷新中；完成后显示更新模型数量，失败时显示错误且允许重试。本次不持久化最后更新时间，避免为单一展示字段增加存储。

## Risks / Trade-offs

- [Risk] 远程源不可用时跨天刷新失败 → 保留当前内存价格，每小时及下次 Popup 展示时重试
- [Risk] 自动检查和手动刷新同时触发 → 使用异步互斥锁串行化刷新
- [Risk] LiteLLM 价格表较大，事件传输成本高 → 事件只携带空 payload，Popup 按需调用 `get_pricing`
- [Risk] 同一天远程价格在自动拉取后再次变化 → 设置页手动刷新强制绕过缓存
- [Risk] Agent 已提供明确成本的记录不受价格表影响 → 保持现有 `agent_cost` 优先语义，并不回写历史记录
